RUNANYWHERE SWIFT API NAMING PROPOSAL
====================================

Review snapshot
---------------
Repository: RunanywhereAI/runanywhere-sdks
Swift SDK: sdk/runanywhere-swift
Branch: siddhesh/flutter-sdk-testing
Commit: 2ea354745be18bf691552b0d2a98236c57d56d28

Goal
----
Make the public API easier to recognize without replacing the flat
RunAnywhere.* facade.

This proposal uses these decision tags:

KEEP       Keep the name and behavior.
RENAME     Change the public name or argument labels.
MERGE      Move the behavior into another public operation.
HIDE       Make implementation or testing plumbing non-public.
ADVANCED   Keep public, but do not present it as a primary app API.

Generated protobuf methods and CppBridge transport methods are outside this
review. They are wire and implementation APIs, not the app-facing SDK.


NAMING RULES
------------

1. Keep RunAnywhere as the main facade.

   Preferred:
     RunAnywhere.generate(...)
     RunAnywhere.loadModel(...)
     RunAnywhere.transcribe(...)

   Rejected for this refactor:
     client.responses.create(...)
     client.local.models.load(...)

2. Use verbs that describe the work:

   list, retrieve, load, unload, download, import, delete, generate,
   transcribe, synthesize, speak, query, register, subscribe.

3. Remove "get" when a noun or a read verb is clearer.

   getUserId()              -> currentUserID()
   getStorageInfo()         -> storageInfo()
   getRegisteredTools()     -> registeredTools()
   getRAGStatistics()       -> ragStatistics()

4. Capitalize initialisms in Swift names and labels:

   modelId                  -> modelID
   organizationId           -> organizationID
   subscriptionId           -> subscriptionID
   supportsLora             -> supportsLoRA
   baseUrl                  -> baseURL

5. Use one operation for one semantic job. Use overloads or request options
   when only the input form changes.

   One generate family should accept text, tools, a structured response
   format, and images. OpenAI, Ollama, and Cactus follow this pattern.

6. Keep separate operations when side effects differ.

   downloadModel stores model files.
   loadModel allocates an inference runtime.
   synthesize returns audio.
   speak synthesizes and plays audio.


PRIMARY RECOMMENDATIONS
-----------------------

1. Keep these names:

   RunAnywhere.initialize
   RunAnywhere.generate
   RunAnywhere.generateStream
   RunAnywhere.loadModel
   RunAnywhere.unloadModel
   RunAnywhere.downloadModel
   RunAnywhere.importModel
   RunAnywhere.listModels
   RunAnywhere.transcribe
   RunAnywhere.transcribeStream
   RunAnywhere.synthesize
   RunAnywhere.synthesizeStream
   RunAnywhere.speak
   RunAnywhere.detectVoiceActivity

2. Build one generation family:

   RunAnywhere.generate(prompt:options:)
   RunAnywhere.generate(_ request:)
   RunAnywhere.generateStream(prompt:options:)
   RunAnywhere.generateStream(_ request:)

   Extend the request to support:

   - messages
   - tools and toolChoice
   - structured response format / JSON schema
   - images

   Deprecate the parallel entry points after the unified request supports
   their result and validation behavior:

   - generateWithTools
   - generateWithStructuredOutput
   - processImage
   - processImageStream

   Keep generateStructured as a typed validation convenience. It does more
   than request constrained output, so merging it without preserving its
   validation result would remove behavior.

3. Keep loadModel and unloadModel.

   OpenAI has no device-model lifecycle API. It selects a hosted model in each
   request. Cactus uses init/destroy on a model object. Ollama loads and unloads
   through special generate requests. On the global RunAnywhere facade,
   loadModel and unloadModel say exactly what happens.

4. Keep downloadModel instead of copying Ollama pull.

   Ollama pull is a strong local-model precedent. Cactus uses download. Mobile
   developers will understand downloadModel without learning registry terms.


PROPOSED CHANGE REFERENCE MATRIX
================================

Reference meaning
-----------------

DIRECT    The proposed public operation closely matches a documented API from
          the named company.
PATTERN   The proposal follows that company's API organization or terminology,
          but is not a direct copy of its signature.
SWIFT     The proposal follows Apple's Swift API Design Guidelines.
INTERNAL  No reviewed company SDK has the same behavior. The proposal improves
          RunAnywhere's own terminology or public boundary.

Multiple references appear only when each one supports the same design choice.
An INTERNAL label is intentional. It is more accurate than claiming that a
company exposes an equivalent API when it does not.
The matrix covers proposed renames, merges, and visibility changes. Unchanged
KEEP decisions remain documented in the full mapping below.

  ps lists loaded/running models.
  Ollama sends tools, structured formats, and images through chat/generate.
  Its REST API loads/unloads through special generate requests, so those names
  should not replace RunAnywhere.loadModel/unloadModel.

MIGRATION PLAN
==============

Phase 1: Approve names
  Review this file and mark each RENAME/MERGE/HIDE decision accepted or rejected.

Phase 2: Add aliases
  Add proposed APIs as thin wrappers over the existing implementations.
  Do not change C++ or protobuf contracts for naming-only work.

Phase 3: Test parity
  Verify each old and new function produces the same request, result, event
  order, cancellation behavior, and errors.

Phase 4: Deprecate old names
  Mark old Swift APIs deprecated with fix-it messages. Keep them through the
  current major release.

Phase 5: Port the approved semantic names
  Implement matching Kotlin, Flutter, and React Native names with native async
  and stream types. Match behavior and argument meaning; do not force identical
  language syntax.

Phase 6: Remove old names
  Remove deprecated aliases only in a major release. Publish a migration table
  and update all examples before that release.
